# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This repo is porting `stravaV10` — a bicycle GPS computer firmware for a custom nRF52840 PCB, currently on Nordic's legacy nRF5 SDK v16 + s340 (BLE+ANT) softdevice — to nRF Connect SDK (sdk-nrf) + Zephyr. `stravaV10/` is the original firmware (its own git repo/remote, unrelated history); `ncs/` is the new west workspace for the port. There is no ported application yet — only the toolchain/workspace has been stood up so far.

## Commands

### Zephyr/NCS workspace (`ncs/`) — the active port target

Activate the environment first, in every new shell:
```
source /home/vincent/Github/StravaV11/.venv/bin/activate
cd /home/vincent/Github/StravaV11/ncs
```

Build (from inside `ncs/`):
```
west build -p always -b native_sim <app-dir> -d <build-dir>       # host simulation, no hardware
west build -p always -b nrf52840dk/nrf52840 <app-dir> -d <build-dir>  # target dev kit
```
Flash and read console (dev kit only, requires SEGGER J-Link tools + `nrfutil` — both already installed on this machine):
```
west flash --build-dir <build-dir>
# console is /dev/ttyACM0, 115200 8N1 (stty -F /dev/ttyACM0 115200 raw -echo)
nrfutil device list                          # confirm the DK is detected
nrfutil device reset --serial-number <sn>    # reset without reflashing
```
Toolchain facts: NCS v3.2.4 (downgraded from v3.3.4 in Phase 11 — see that section for why), Zephyr SDK 0.17.4 with only the `arm-zephyr-eabi` toolchain installed (target is Cortex-M4 only — do not install other archs; 0.17.4 is also what v3.2.4's own `zephyr/SDK_VERSION` requests, so no toolchain reinstall was needed for the downgrade). `west sdk list` shows what's registered.

### Legacy firmware (`stravaV10/`) — reference only, not actively built here

Real hardware build requires the nRF5 SDK v16 tree + GCC 6 2017-q2-update ARM toolchain (neither is installed in this environment — only the new Zephyr `arm-zephyr-eabi` toolchain is):
```

```

Host-side test/simulation build (business logic + a mocked LCD/GPS/Nordic-API layer, runs on Linux with no target hardware — this is the thing to reuse when porting logic, since it already proves the code is hardware-decoupled):
```
cd stravaV10
mkdir build && cd build
cmake -G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Debug ..

```
`TDD/LS027simulator.jar` renders what the real Sharp LS027 display would show, when built with `-DLS027_GUI` enabled. `TDD/GPX_simu*.csv` are canned GPX replay inputs used by the simulator instead of a live GPS fix.

## Architecture

### Port plan and decisions already made

The full component-by-component inventory (what's hardware-agnostic and portable as-is, what Zephyr replaces outright, what needs a real driver port, and the two biggest feasibility risks — ANT+ support on NCS/Zephyr, and rewriting the BLE central profiles against Zephyr's Bluetooth host API) lives in this session's memory, not duplicated here since it will get stale as the port proceeds; ask about it if picking this project back up mid-port. Decisions locked in so far: ANT+ is being kept (not dropped for BLE-only), the first porting milestone is the hardware-agnostic business-logic layer (`Model`, `routes`, `Boucle*`, `filters`, `kalman`, `VParser`, `komoot_nav.c`) validated on `native_sim` before any driver/board work, hardware bring-up targets the nRF52840-DK before the custom PCB, and the separate `AP/` companion-dongle firmware is out of scope for this effort.

### `stravaV10` structure (legacy firmware being ported)

- **Business logic (hardware-agnostic C/C++, proven portable by the TDD host harness)**: `source/Model.*`, `source/model/*` (Attitude, Locator, PowerZone, RRZone, SufferScore, UserSettings), `source/routes/*` (GPX/segment geometry), `source/model/Boucle*` (CRS/FEC/Zwift ride-loop state machines), `libraries/filters`, `libraries/kalman`, `libraries/VParser`, `libraries/komoot/komoot_nav.c`.
- **UI**: `source/vue/*` (menu system, screens per mode) drawn via `libraries/AdafruitGFX` onto the custom `drivers/lcd/ls027.c` Sharp memory LCD driver.
- **Connectivity**: `libraries/ant_profiles/*` (ANT+ FE-C/HRM/cadence-speed/glasses) and `libraries/ble_services/*` (`ble_cp_c`, `ble_lns_c`, `ble_komoot_c` — BLE GATT central profiles), both written against SDK16 APIs (`nrf_ble_*`, Peer Manager, ANT stack) that don't exist on Zephyr.
- **Sensors**: `source/sensors/*` — `bme280` (baro) and `fxos` (FXOS8700 accel/mag) have upstream Zephyr drivers; `ms5637`, `STC3100` (fuel gauge), `VEML6075` (UV), `fram` do not and need custom Zephyr drivers.
- **Storage**: `source/sd/*` (SD/FatFS) and `libraries/SST` (external NOR flash chips) map onto Zephyr's `disk_access`/`flash`/`fs` subsystems.
- **SDK16 glue that gets trashed, not ported**: `libraries/task_manager`+`task_manager_wrapper*` (Zephyr threads/work queues/timers instead), `drivers/gpio.c`/`i2c.c`/`spi.c`/`uart.c` (devicetree + Zephyr drivers instead), `libraries/hardfault`, `helper.*`/`math_wrapper*`/`assert_wrapper.h`, `dfu/` + the old bootloader (MCUboot instead), `pca10056/`/`hw_test/`/`custom_board_v*.h` (new devicetree board def instead), `libraries/rtt`/`sysview`/`jscope` (Zephyr's native RTT/SystemView backends instead).
- **Out of scope**: `AP/` (separate BLE-UART bridge dongle firmware), `zpm/` (Node.js PC-side GPX/segment tooling, not firmware).

### `ncs/` structure (new west workspace)

Standard NCS layout: `nrf` (the manifest repo, sdk-nrf), `zephyr` (pinned via NCS manifest, currently `ncs-v3.2.4` — see Phase 11 for why this is older than the `v3.3.4` this workspace started on), `nrfxlib`, `bootloader` (mcuboot), `modules`, `tools`.

`stravaV11_app/` is the freestanding application holding the Phase 1 port (see below) — the only application under this workspace so far. Build it with:
```
west build -p always -b native_sim/native/64 stravaV11_app -d <build-dir>       # host, run zephyr.exe directly
west build -p always -b nrf52840dk/nrf52840 stravaV11_app -d <build-dir>        # DK, then west flash --build-dir <build-dir>
```
Use the `native_sim/native/64` qualifier, not plain `native_sim` — the latter defaults to a 32-bit build, and this machine's g++ 14 doesn't have the 32-bit multilib libstdc++ headers installed (only g++13's are present), so it fails with a `bits/c++config.h: No such file or directory` error.

#### Phase 1 status: business-logic port (done, validated on both native_sim and the DK)

`stravaV11_app/lib/` holds copies (not symlinks — `stravaV10` stays untouched as the reference) of the hardware-agnostic tier identified in the architecture survey: `source/routes/*`, `source/model/{PowerZone,RRZone,SufferScore,UserSettings}`, `source/display/{SegmentManager,Zoom}`, `libraries/{kalman,VParser,komoot,filters,utils}`, plus the small SDK16 wrapper headers (`segger_wrapper.h`, `math_wrapper.h`, `assert_wrapper.h`, `task_manager_wrapper.h`) — these are kept building under `-DTDD`, reusing stravaV10's existing host-build abstraction (they already compile to hardware-free stubs that way) rather than writing new Zephyr-native shims prematurely; that substitution is follow-up work for when the driver phases land. `src/main.cpp` is a smoke test (not a ztest suite yet) exercising each ported piece; output is bit-identical between native_sim and the flashed DK.

Three things worth knowing if you touch this again:
- **`libraries/filters/order1_filter.c` was swapped for `TDD/order1_filter_tdd.c`.** The former is the real ARM CMSIS-DSP implementation (references a `.instance` struct member that only exists in the non-`TDD` branch of `order1_filter.h`) — stravaV10's own CMakeLists.txt already substitutes the TDD variant for host builds; we do the same.
- **`Point::objectCount` / `Point2D::objectCount2D`** (static members declared in `Points.h`) are defined in stravaV10's `Model.cpp`, not `Points.cpp` — an artifact of Model.cpp being the catch-all file, not a bug. Since Model.cpp isn't ported, these two one-line definitions live in `src/globals.cpp` instead, along with the `UserSettings u_settings` global instance that `PowerZone::addPowerData()` reads FTP from.
- **Adapters for the two real hardware calls this tier still makes**, in `stravaV11_app/adapters/`: `notifications_segNotify()` (drives the WS2812 status LED from `SegmentManager`) no-ops; `fram_read_block()`/`fram_write_block()` (from `UserSettings::sync()`/`writeConfig()`) return `false`, so settings never persist and always fall back to `resetConfig()`'s in-memory defaults. Both get replaced for real once the LED and FRAM driver phases happen. `ant_device_manager.h` here is also a placeholder — just the four default ANT device-number constants `UserSettings::resetConfig()` needs, not the real header (which pulls in the full ANT stack via `ant.h`).

Not part of this slice, and why: `Model.cpp` (the hardware/connectivity orchestrator), `Boucle*.cpp` (ride-mode controllers — `Boucle.cpp` itself pulls in the task manager, global `vue`/`stc` objects, and `g_structs`-based error state; `BoucleFEC.cpp` pulls in ANT+ FE-C and BLE), `Attitude.cpp`/`Locator.cpp` (need the FXOS sensor driver and TinyGPS++ integration respectively), `UserSettings`'s FRAM persistence, and all connectivity (`ble_services`, `ant_profiles`) — these need actual driver/connectivity phases first, per the phased plan.

#### Phase 2 status: DK driver bring-up (in progress)

`stravaV11_fw/` is a second, separate application (not merged into `stravaV11_app`) for hardware bring-up on the nRF52840-DK: GPIO/LED/button and the LS027 display. It's kept separate because it depends on DK-specific devicetree (an `&arduino_spi` node, a `zephyr,display` chosen node) that doesn't exist on `native_sim` — mixing it into the native_sim-validated logic app would break that app's portability. The two apps get merged once both are mature.
```
west build -p always -b nrf52840dk/nrf52840 stravaV11_fw -d <build-dir>
west flash --build-dir <build-dir>
```

Key finding: **Zephyr already has an upstream driver for this exact display.** `zephyr/drivers/display/ls0xx.c` (devicetree compatible `sharp,ls0xx`) explicitly lists `LS027B7DH01A` as supported hardware, and its binding's `serial-vcom-inversion` property matches stravaV10's own `drivers/lcd/ls027.c` approach (VCOM toggled in-band over SPI, no EXTCOMIN pin) — so no custom driver was needed, just a devicetree overlay (`stravaV11_fw/boards/nrf52840dk_nrf52840.overlay`) wiring a `sharp,ls0xx` child node (400x240, `serial-vcom-inversion`) onto the DK's Arduino-header SPI bus (`arduino_spi`/spi3). There's also a matching Zephyr shield (`boards/shields/ls0xx_generic`) but it defaults to a different variant (128x128, hardware EXTCOMIN) — not a match for our wiring, hence the hand-written overlay instead of `-DSHIELD=`.

**Validated on real hardware** (bare DK, nothing external attached — see [[project_port_scope]]/CLAUDE.md decisions):
- GPIO: on-board LED toggling and button read.
- UART: implicitly proven the whole time — the console itself is over UART (J-Link's CDC-ACM bridge).
- I2C: a full 0x08-0x77 address scan on `arduino_i2c` (i2c0) comes back as 112 clean NACKs, 0 ACKs — expected with no sensor attached, and importantly the bus completes every transaction rather than hanging.
- SPI + display: the display subsystem initializes (`spi_is_ready_dt()` passes — it only checks the SPI *controller*, not a peripheral handshake, so this succeeds even with nothing wired to the bus) and `display_write()` returns 0 for a full-frame test pattern.

**Not validated, and can't be until the display is physically wired up:** that the SPI protocol framing actually produces correct pixels on real glass, or the exact pin assignment (the overlay's pins are arbitrary DK Arduino-header pins, explicitly not the final custom-PCB mapping — that comes in the later custom-PCB bring-up phase). Phase 2 is otherwise done.

#### Phase 3 status: sensors (partly done — two free wins, three need real custom driver work)

Added to `stravaV11_fw`'s overlay/prj.conf/main.c, same bare-DK caveat as the display (nothing physically attached, so these validate clean init/error paths, not real readings):

- **`bme280`** (0x76) — Zephyr's upstream `bosch,bme280` driver, direct reuse. This is stravaV10's *active* barometer (`BARO_TYPE bme280` in `source/parameters.h`); `ms5637.c` in stravaV10 is an alternate-BOM option for different hardware revisions and shares the same 0x76 address (the two are never populated on the same board).
- **`fxos8700`** (0x1e) — Zephyr's upstream `nxp,fxos8700` driver, direct reuse. On the DK it correctly logs `Could not get WHOAMI value` and reports not-ready — proves the presence-check path works, not that it works with a real chip yet.
- **FRAM → `fujitsu,mb85rcxx`** (0x50, `address-width = 8`, `size = 2048`) — reused, not custom-built. Traced stravaV10's `source/sensors/fram.c` addressing scheme (`twi_address |= (block_addr & 0x700) >> 8`, i.e. high address bits folded into the low bits of the 7-bit I2C address) against the Zephyr driver's `mb85rcxx_translate_address()` (`cfg->i2c.addr + (offset >> cfg->addr_width)`) and confirmed they're the same scheme — not a guess. `eeprom_write()` correctly returns `-5` (I/O error) with nothing attached.

**Still need real custom Zephyr drivers** (not written yet — this is genuine remaining work, not just unvalidated):
- **`ms5637`** — Zephyr has `drivers/sensor/meas/ms5607` (a sibling chip) but it is **not** a safe alias: compared stravaV10's own `ms5637_compute_t_p()` against the ms5607 driver's `ms5607_compensate()` line by line. The first-order compensation and coefficient layout match, but the second-order low-temperature term differs (`sens2 = 29 * tx / (1<<4)` in stravaV10's MS5637 code vs `SENSi = 2 * temp_sq` in the ms5607 driver) — aliasing the two would build and run fine but silently give a slightly wrong reading below 20°C. Since `ms5637` isn't even the active barometer choice, this is low priority.
- **`STC3100`** (fuel gauge/coulomb counter, address 0x70) — no upstream analog; Zephyr's `sbs_gauge` driver targets SBS-compliant gauges, a different protocol family entirely.
- **`VEML6075`** (UV sensor) — no upstream analog; Zephyr has `veml7700`/`veml6031`/`veml6046` (different Vishay parts, different register maps), none matching VEML6075. Gated behind `PROTO_V11` in stravaV10, which — despite the name — is the flag for the *current* (v3) board revision, not a deprecated prototype, so this sensor is genuinely part of the active hardware, just not yet portable for free.

#### Phase 4 status: storage (done — real hardware validated for flash, SD stays a clean-failure placeholder)

- **QSPI NOR flash — fully validated on real hardware, not just a clean-init check.** The nRF52840-DK has a genuinely populated on-board QSPI NOR chip (MX25R6435F, 64Mbit, `&qspi`/`mx25r64` in the DK's own default devicetree — no overlay needed to reach it). `qspi_flash_demo()` in `stravaV11_fw/src/main.c` does a real `flash_erase()` → `flash_write()` → `flash_read()` round trip against it and the pattern comes back byte-for-byte correct. stravaV10's own external flash is a different chip (MT25QL128, `libraries/SST/mt25.c`) but the same JEDEC SPI-NOR-over-QSPI family, so this is a legitimate stand-in for that storage path — the first piece of Phase 2-4 that's actually hardware-proven end-to-end, not just "doesn't hang."
- **Original plan was FAT-over-QSPI-flash** (`zephyr,flash-disk` + `disk_access` + `CONFIG_FAT_FILESYSTEM_ELM`, mirroring stravaV10's actual FatFs usage) but hit a real NCS-specific wall: this workspace's Partition Manager is unconditionally active for any app built here (its Kconfig literally says "read-only, do not change" — it isn't something `prj.conf` can turn off), and `flashdisk.c`'s build only works for partitions PM itself allocated and tagged with "disk" affiliation metadata. A hand-written devicetree `fixed-partitions` node isn't visible to PM's scan, which broke the build (`PM_FOREACH_AFFILIATED_TO_disk` expanding to nothing). The real fix is a `pm_static.yml` statically registering the partition with PM — a genuine follow-up item, not done here; descoped to the direct flash API instead, which still proves the chip works, just not the filesystem layer on top of it.
- **SD card over SPI** (`zephyr,sdhc-spi-slot` + `zephyr,sdmmc-disk`, placeholder pins on `arduino_spi`, same caveat as the display/sensors) — cleanly reports "no card" (`Card error on CMD0`, `disk_access_ioctl` returns `-116`) rather than hanging. stravaV10's SD path (`source/sd/diskio_sdc.c`) is the old nRF5 SDK's `nrf_block_dev_sdc` component doing the same SD-over-SPI protocol.

### Phase 5 status: connectivity — ANT+ feasibility spike done (research only, no code yet)

Nordic's own sdk-nrf ships **zero** ANT+ code (confirmed by grepping the actual `ncs/` checkout — nothing beyond an unrelated `variant` substring match). ANT+ is technically feasible, but only via a separate, access-gated add-on:

- **"ANT for nRF Connect SDK"** (https://ant-nrfconnect.github.io/), published by ANT Wireless (a Garmin division), currently v2.1.1. Explicitly supports nRF52840. Confirmed compatibility matrix pairs sdk-nrf v3.2.4 with sdk-ant v2.1.0/2.1.1 — our pinned v3.3.4 isn't explicitly listed, so **verify/re-check version compatibility before starting real integration work**, don't assume the patch gap is fine.
- **Concurrent operation with Bluetooth is a documented, real use case**, not experimental: `CONFIG_BT` + `CONFIG_ANT` together, described as "Multiprotocol: ANT and Bluetooth® LE" — this is exactly what stravaV10 needs (ANT+ sensors + BLE central profiles simultaneously). The underlying coexistence mechanism (MPSL timeslots, presumably, since `nrfxlib/mpsl/include/mpsl_timeslot.h` is present and this is the standard Nordic mechanism for this kind of sharing) isn't detailed in the public docs.
- **Access**: free "ANT+ Adopter" account (accept a license agreement, authenticate via GitHub) — no cost for a hobby/non-commercial project. Integration is a west manifest add-on step (not yet done — no `ant` module in this workspace).
- **Hardware**: requires the 32.768kHz LF crystal (X2) with ≤50ppm tolerance — both the nRF52840-DK and stravaV10's custom PCB have this already (standard for BLE timing regardless of ANT+).

**Ecosystem context surfaced during this research, reaffirmed with the user 2026-09-06**: Garmin ended the ANT+ certification and paid membership program on 2025-06-30 (EU Radio Equipment Directive now requires authenticated/encrypted wireless transmission of personal data like heart rate; ANT+'s optional encryption isn't enforced by the installed base, and Garmin chose to wind the program down rather than break compatibility). The free Adopter tier, device profiles, docs, and this SDK remain available — nothing here blocks this project — but industry commentary (DC Rainmaker, 5kRunner) describes the broader ecosystem as being in decline. User's call: proceed with ANT+ as originally planned regardless.

Not started yet: the actual `ant` west module integration, and `ble_lns_c`/`ble_komoot_c` (only `ble_cp_c` is ported so far — see below).

#### Phase 5 status: BLE central — Cycling Power Service client ported and validated on real hardware

`ble_cp_c` (Cycling Power Service, UUID 0x1818) is ported to `stravaV11_fw/lib/bt_cp_client.{h,c}`, following the structure of NCS's own `bt_hrs_client` (`nrf/subsys/bluetooth/services/hrs_client.c`) — the closest upstream analog, since neither Zephyr nor NCS ships a Cycling Power Service *client* (they have plenty of GATT *server* services like `hrs`/`bas`, but writing your own client against `bt_scan` + `bt_gatt_dm` is the normal NCS pattern, demonstrated by `nrf/samples/bluetooth/central_and_peripheral_hrs`, which `stravaV11_fw/src/ble_demo.c` mirrors). The wire-format parsing (`cp_measurement_parse()`/`cp_vector_parse()` in `bt_cp_client.c`) is a direct port of stravaV10's `power_measure_decode()`/`power_vector_decode()` — same Bluetooth SIG GATT Specification Supplement fields, just `sys_get_le16/32()` instead of Nordic's `uint16_decode`/`uint32_decode`. No pairing/bonding, matching stravaV10 (cycling power meters are normally open GATT servers).

**Validated on real hardware, not just build success**: flashed to the DK, the SoftDevice Controller and Bluetooth host fully initialize (`Identity: E6:14:C4:12:F1:E8 (random)`, HCI/LMP version negotiated), and scanning starts cleanly. Hit and fixed one real bug this way: `bt_scan_filter_add()` failed with `-ENOMEM` until `CONFIG_BT_SCAN_UUID_CNT=1` was set (its Kconfig default is 0 filter slots — not obvious from the API alone). No Cycling Power peripheral was nearby to complete the discovery/subscribe path, so — same tier as the sensors/display — this proves the BLE stack and scan/filter path work correctly, not that the notification parsing produces correct values against a real sensor yet.

**`ble_lns_c` (Location and Navigation Service) and `ble_komoot_c` (custom Komoot navigation service) are out of scope by user decision (2026-09-06) — not being ported.** `bt_cp_client` is the only BLE central profile from stravaV10 that's part of this port. Wiring `bt_cp_client` into the ported `Model`/`Boucle*` logic from Phase 1 is still a later step (same as the driver-to-logic wiring gap noted in earlier phases).

#### Phase 5 status: ANT+ integrated and validated on real hardware

The user obtained ANT+ Adopter access and downloaded `sdk-ant-2.1.1` (from `github.com/ant-nrfconnect/sdk-ant`) to `~/Downloads/sdk-ant-2.1.1/`, then copied into this workspace at `ncs/ant/` — **gitignored, never commit it** (proprietary, license-gated vendor source; see `.gitignore`'s comment). It's a proper Zephyr module (has `zephyr/module.yml`), so it's consumed via `ZEPHYR_EXTRA_MODULES` in `stravaV11_ant/CMakeLists.txt` rather than a west manifest import — this avoids the workspace-topology conflict raised during the feasibility spike (sdk-ant's own `west.yml`, used only when it's the manifest root, pins sdk-nrf v3.2.4; we stayed on our existing v3.3.4 per the user's explicit choice to "just try the current version" rather than creating a second workspace or downgrading).

**That version gap was real, not hypothetical, but narrow and fixed**: `ant/Kconfig`'s `ANT_LIB_DIR` (which selects the correct precompiled `libant.a` variant to link) computed empty because it only checked `SOC_SERIES_NRF52X`, a Kconfig symbol Zephyr has since deprecated and renamed to `SOC_SERIES_NRF52` (in our v3.3.4 / Zephyr 4.3.99 — it now only `select DEPRECATED`, selected by nothing for a real nRF52840 build). Fixed with a one-line local patch to `ant/Kconfig` (`default "nrf52" if SOC_SERIES_NRF52X || SOC_SERIES_NRF52`) — not upstreamed, just a local workaround since that file isn't tracked here anyway. `ANT_LIB_DIR` has no Kconfig prompt, so it can't be overridden from a `.conf` fragment (Zephyr's Kconfig rejects that outright) — the Kconfig source itself had to change.

`stravaV11_ant/` (new, separate from `stravaV11_fw` — kept isolated deliberately since this was the first-ever build of unfamiliar, version-mismatched vendor code) is a minimal test: `ant_init()` + one wildcard slave RX channel (device number/type/transmission type all 0, RF freq 66 / 2466MHz, period 8192 / 4Hz — same defaults as `ant/samples/ant_broadcast_rx`), evaluation license key (`CONFIG_ANT_EVALUATION_KEY=y` — appropriate since this is a non-commercial hobby project, not a product being sold). Uses `CONFIG_ANT` only, not yet combined with `CONFIG_BT` (the documented multiprotocol path) — that combination, and porting stravaV10's actual profiles (`rf/fec.c`/`hrm.c`/`bsc.c`/`glasses.c` against `ant/include/ant_profiles`), are still open.

**Validated on real hardware**: flashed to the DK, console shows `ANT stack initialized, version 2.01.01` and `ANT wildcard RX channel open, listening...` — the radio genuinely opened a channel, not just a clean error path. No ANT+ broadcaster was nearby to receive from, so (same tier as BLE/sensors) actual message reception is still unproven.

**Update: ANT+ and BLE now combined and validated together, in `stravaV11_fw` itself** (not just the isolated `stravaV11_ant` test). `stravaV11_fw` gained the same `ZEPHYR_EXTRA_MODULES` wiring for `ant/`, plus `CONFIG_ANT`/`CONFIG_ANT_CHANNEL_CONFIG`/`CONFIG_ANT_EVALUATION_KEY` alongside its existing BLE config, and a new `src/ant_demo.c` (the same wildcard-RX logic as `stravaV11_ant`). Call order matters and is deliberate: `main()` calls `ant_demo_start()` *before* `ble_demo_start()`, matching `ant/samples/ble_ant_app_hrm` (sdk-ant's own combined reference sample) — both ANT and the SoftDevice Controller sit on MPSL, and that sample brings ANT up first, with no `CONFIG_ANT_SDC_INIT` needed either way. Flashed to the DK: ANT initializes and opens its channel, then the SoftDevice Controller and Bluetooth host initialize immediately after with no errors, and both keep running concurrently (scanning + ANT RX) for 15+ seconds with no crash or conflict — the documented "Multiprotocol: ANT and Bluetooth LE" capability, genuinely confirmed on this hardware/SDK-version combination, not just asserted by the docs.

`stravaV11_ant` (the isolated single-protocol test) is left in place as a smaller reference/repro case; it isn't superseded, just no longer the only place this code runs.

**Reviewed with the user 2026-09-06 — clarifying what "ANT+ is ported" actually means so far: infrastructure only, no device profiles yet.** `ant_demo.c`'s wildcard channel (device type/number/transmission type all 0) is not a port of any of stravaV10's real ANT+ profiles — it only proves the ANT+ stack and radio work. stravaV10's actual profile layer, none of it ported yet:
- `rf/fec.c` (308 lines) — FE-C, controls a smart trainer's resistance (ERG/slope mode).
- `rf/hrm.c` (202 lines) — heart rate monitor.
- `rf/bsc.c` (318 lines) — bike speed/cadence.
- `rf/glasses.c` (121 lines) — a custom/niche display-glasses protocol, worth confirming is still wanted before porting.
- `rf/ant_device_manager.cpp` (131 lines) — pairing/search orchestration across all of the above.

**Found while reviewing**: `ncs/ant/lib/ant_profiles/` ships ready-made `ant_hrm` and `ant_bsc` profile libraries — the same free-win pattern as `bme280`/`fxos8700` in Phase 3, directly matching `hrm.c`/`bsc.c`'s needs. Root cause: sdk-ant doesn't read a header for this at all — `ant/init/ant_init.c`'s `ant_stack_init()` call reads the Kconfig string `CONFIG_ANT_LICENSE_KEY` directly, so a `#define ANT_LICENSE_KEY "..."` header has no effect on this build regardless of whether it's included anywhere.

Kept `ANT_license.h` as the single place the user maintains the key (rather than asking them to duplicate it into a second gitignored file) since Kconfig can't include a C header directly. If the header is missing (e.g. a fresh checkout without it), both branches degrade to a `message(WARNING ...)` and the public evaluation key, so the build still succeeds either way rather than failing hard.

**Validated**: rebuilt for `nrf52840dk/nrf52840`; the west log showed `Merged configuration '.../ant_license_generated.conf'`, and the resulting `zephyr/.config`'s `CONFIG_ANT_LICENSE_KEY` value no longer matches sdk-ant's known public evaluation key string — confirming the real key is now what's actually compiled into the firmware, without ever putting that key's value into a tracked file or a commit.

### Phase 7 status: UI graphics (done — the portable drawing library + a new display bridge; the actual screens are deliberately out of scope)

stravaV10's UI (`source/vue/*`, ~4500 lines) turned out to be a much more tightly coupled "god class" than the other subsystems ported so far: `Vue` multiply-and-virtually inherits from `VueCRS`, `VueFEC`, `VuePRC`, `VueDebug`, `NotifiableDevice`, and `Menuable` all at once (a diamond hierarchy sharing one `Adafruit_GFX` base), and `VueCRS` etc. declare pure-virtual `cadran()`/`Histo()`/... that only `Vue.cpp` implements — none of these classes build or mean anything in isolation the way `PowerZone` or `Locator` did. Porting the whole thing would mean pulling in `Model`, `Boucle*`, buttons, and notifications all at once, which is exactly the "orchestration layer" category deferred since Phase 1. So this phase ported the genuinely independent, reusable piece instead:

- **`libraries/AdafruitGFX` (`Adafruit_GFX.{h,cpp}`, `Print.{h,cpp}`, `Printable.h`, `pgmspace.h`, `gfxfont.h`, `glcdfont.c`, the `Org_01` font) — ported unmodified**, already fully portable (confirmed by checking every include, same as every other library in this port). One real, generic C/C++ portability fix needed: `pgmspace.h` used bare `typeof`, a GNU extension that's unavailable under this toolchain's strict `-std=c++17` (only the always-available `__typeof__` is) — a 4-line `sed` fix, not an SDK-version issue like Phase 5's ANT+ Kconfig gap.
- **New: `ZephyrGFX` (`source/vue/ZephyrGFX.{h,cpp}`)**, a from-scratch `Adafruit_GFX` subclass — stravaV10 never needed this class because its `Vue::drawPixel()` called its own hand-rolled `LS027_drawPixel()` directly; we're on Zephyr's upstream `sharp,ls0xx` driver instead (Phase 2), which only exposes the generic `display_write()` API, not per-pixel calls. `ZephyrGFX` implements `drawPixel()` against an in-memory 400x240 1bpp buffer matching what `ls0xx.c` expects (`PIXEL_FORMAT_MONO01`, **LSB-first** per byte) — deliberately *not* the same bit order as stravaV10's own `ls027.c` (which packed MSB-first) — and exposes the raw buffer for a caller to push via `display_write()`. It also does *not* replicate stravaV10's hardcoded rotation=3 screen transform (case-mounting-specific; needs real glass to get right, so left for later). The class itself is hardware-free (no Zephyr includes) so it builds and runs on `native_sim`.
- **Verified with a real before/after pixel-count check, not just "didn't crash"**: `stravaV11_app`'s smoke test fills the buffer black, draws text (real font rasterization via `Org_01`) plus rect/line primitives, and checks the set-pixel count actually increased (0 → 1675) — the first version of this test filled white-on-white and would have "passed" even if `drawPixel()` were a no-op, which is worth remembering as a pattern to watch for when writing pixel/graphics smoke tests.
- **Hardware tier**: `stravaV11_fw` gained the same `AdafruitGFX`/`ZephyrGFX` code plus a new `src/gfx_demo.cpp` that draws the same kind of scene and pushes it via `display_write()` to the real `sharp,ls0xx` device from Phase 2. Flashed to the DK: `5353 pixels set` then `display_write() -> 0` — the full pipeline (font rasterization → buffer → SPI) runs cleanly on real hardware. Same caveat as Phase 2 throughout: no physical LS027 is attached, so pixel-level correctness on real glass is still unverified.

Building this pulled in the same `-DTDD` wrapper-header bridge used throughout `stravaV11_app` (needed because `Adafruit_GFX.cpp`/`WString.cpp` have `#ifndef TDD` branches using AVR-only builtins like `__isnanf`) — first time that bridge crossed over into `stravaV11_fw`, which also needed `CONFIG_CPP`/`CONFIG_REQUIRES_FULL_LIBCPP` added (the TDD headers need `<cstdio>`, unavailable under Zephyr's default minimal C++ runtime).

**Not ported, and why**: `Vue`/`VueCRS`/`VueFEC`/`VuePRC`/`VueDebug`/`VueGPS` (the actual screens), `MenuObjects`/`Menuable` (menu widget system), `Screenutils`, `button.h`/`Notif.h` — all of it is orchestration tightly coupled to `Model`, `Boucle*`, buttons, and notifications, none of which are ported yet. This is the same category and same reasoning as `Model.cpp` since Phase 1, just now confirmed to also cover the UI layer specifically.

### Phase 8 status: scheduling/power (done — three Zephyr-native replacements, all validated running concurrently on real hardware)

`libraries/task_manager` (stravaV10's hand-rolled cooperative scheduler) was flagged as "trash, replaced by Zephyr threads/work queues" all the way back in the Phase 1 architecture survey. Phase 8 is that replacement actually happening, plus the two other pieces of `source/scheduling/`:

- **`task_manager` → Zephyr threads + `k_event`** (`stravaV11_fw/src/task_demo.c`). Not a 1:1 API clone of `w_task_events_wait()`/`w_task_events_set(task_id, mask)` (a generic "target any task by ID" indirection over one shared flags word per task) — Zephyr's `k_event` doesn't need that indirection, so each logical task just gets its own `k_event` object and producers call `k_event_set()` on the specific one directly. E.g. Locator's `w_task_events_set(m_tasks_id.boucle_id, TASK_EVENT_LOCATION)` becomes `k_event_set(&boucle_events, TASK_EVENT_LOCATION)` once Locator/Boucle are actually ported (not yet — this is infrastructure, demonstrated with a stand-in producer/consumer thread pair). `task_delay()`/`task_manager.c`'s custom tick-management loop (`task_tick_manage()`) has an even simpler replacement: every Zephyr thread already has `k_sleep()` built in.
- **`power_scheduler.cpp` → a Zephyr thread doing the same `k_uptime`-based idle check** (`power_demo.c`), same logic as `power_scheduler__run()`/`power_scheduler__ping()` but with a 4-second demo timeout instead of stravaV10's real 15 minutes (`POWER_SCHEDULER_MAX_IDLE_MIN`) — that constant belongs at the call site once `Boucle` is ported, not in the replacement's logic. On real timeout, stravaV10 drives either a fuel-gauge shutdown command or a `KILL_PIN` GPIO; Zephyr's equivalent, `sys_poweroff()` (nRF52 series has `select HAS_POWEROFF`), is genuinely available but **deliberately not called** in the demo — it would actually power off the DK mid debug-session with no wake source wired up. Logs a stand-in message instead.
- **`i2c_scheduler.cpp` → `k_work_delayable`** (`poll_demo.c`). Despite the name, that file was never a generic I2C queue — Zephyr's I2C driver already handles transaction queuing/locking internally, which is why Phase 3 never needed one. It's really the periodic-sensor-poll orchestrator; `poll_demo.c` demonstrates the direct Zephyr replacement (a self-resubmitting `k_work_delayable`) against the real `bme280` device from Phase 3, at stravaV10's actual poll period (`BARO_REFRESH_PER_MS`, 100ms).

**Validated together on real hardware, not in isolation** — this is the first phase where the interesting thing to prove was concurrent correctness, not just "one driver doesn't hang," and native_sim wouldn't have shown that as convincingly as real preemption on the target: flashed to the DK, all three run alongside everything from Phases 2-7 simultaneously. Observed in the log: the poll thread fires cleanly 5 times at 100ms spacing; the producer/consumer threads hand off `TASK_EVENT_LOCATION` five times with correct wait/clear/process ordering each time; the idle-timeout thread fires at 4001ms (just past its 4000ms threshold) mid-run, logs its stand-in message, and — critically — the other threads (task_demo's 5th producer/consumer handoff) keep running correctly afterward, confirming the idle-timeout path didn't disturb anything else. `CONFIG_EVENTS=y` was the one new Kconfig needed for `k_event`.

### Phase 9 status: USB CDC-ACM (done — device controller validated on real hardware; host-side enumeration not yet checked, needs a second cable)

stravaV10's `source/usb/usb_cdc.c` is a composite CDC-ACM (console) + MSC (mass storage, exposing the SD card/NOR flash as a USB drive to unload GPX/segment files) device. Only the CDC-ACM half is ported here — **MSC is a known, explicit gap**: Zephyr's USB MSC class needs a `disk_access`-registered block device, and Phase 4 deliberately didn't get the QSPI flash that far (the NCS Partition Manager issue documented there) while the SD card has no card inserted anyway. A real SD card, or resolving that Phase 4 gap, would unblock it.

- **`stravaV11_fw/src/usbd_init.{h,c}`**: adapted from Zephyr's own `samples/subsys/usb/common/sample_usbd_init.c` (the standard, correct way to configure the new USB device stack) but de-sample-ified — that file's own header explicitly says "you should not use it in your own application" (it depends on `Kconfig.sample_usbd`, documented as only sourced for in-tree Zephyr samples). Our copy defines its own VID/PID/strings directly instead. VID `0x2FE3` is still the Zephyr Project's placeholder VID (same one the sample uses) — fine for this bring-up/personal-project stage (same category as Phase 5's ANT+ evaluation license key), but a real product needs its own purchased VID before shipping.
- **`stravaV11_fw/src/usb_demo.c`**: enables the CDC-ACM class and logs VBUS/DTR transition messages via the USBD message callback, same pattern as Zephyr's `cdc_acm` sample — except it does **not** block waiting for DTR the way that sample does (it calls `k_sem_take(&dtr_sem, K_FOREVER)`, which would hang this smoke test forever with no host terminal attached).
- **Two real bugs hit and fixed while wiring this up**: a stray `*/` inside my own explanatory comment (`USBD_DESC_*/` — the `*/` closed the C block comment early, corrupting everything after it into broken syntax); and a link-time symbol collision — `LOG_MODULE_REGISTER(usbd_init, ...)` collided with Zephyr's own internal log module of the identical name in `zephyr/subsys/usb/device_next/usbd_init.c`, fixed by renaming ours to `stravav11_usbd_init`.

**Fully confirmed on real hardware, including host-side enumeration**: the on-die USB device controller initializes correctly (`udc_nrf: Preinit` / `udc_nrf: Initialized`), the USBD stack builds a valid descriptor set (`bNumInterfaces 2 wTotalLength 75`), and everything from Phases 2-8 keeps running correctly alongside it. The user connected a second USB cable to the DK's own USB connector (separate from the J-Link cable already in use for flashing/console), and it enumerates exactly as configured: `lsusb` shows `ID 2fe3:0002 NordicSemiconductor stravaV11 GPS computer` (our VID/PID/manufacturer/product strings), and a working `/dev/ttyACM1` appears (`/dev/serial/by-id/usb-stravaV11_stravaV11_GPS_computer-if00`), distinct from the J-Link's `/dev/ttyACM0`. This is the strongest hardware validation of any peripheral in this port so far — most others can only confirm "clean init, no peer attached"; this one has independently-observable host-side proof.

### Phase 10 status: bootloader/DFU (core done — MCUboot boots the real app, validated on hardware; actual over-the-air update cycle not attempted)

stravaV10's `dfu/` is a full nRF5 SDK "secure DFU bootloader" (`nrf_bootloader`/`nrf_dfu`, MBR-based, entered by holding a button at power-on, updates delivered over USB with `dfu_public_key.c` signature verification). Its Zephyr/NCS replacement, MCUboot, was already sitting in the workspace at `bootloader/mcuboot` since Phase 1 but unused until now.

**One line of config was all it took**: `stravaV11_fw/sysbuild.conf` with `SB_CONFIG_BOOTLOADER_MCUBOOT=y`. Worth noting explicitly: this is **mainline Zephyr's own sysbuild MCUboot integration** (`zephyr/share/sysbuild/images/bootloader/Kconfig`), not NCS's older Partition Manager-based path — it partitions via devicetree `fixed-partitions`, so it didn't reopen the PM/flash-disk friction from Phase 4 (that was specific to `disk_access`'s flashdisk driver's PM affiliation metadata, a different mechanism than boot-slot partitioning).

Enabling it: image got signed (`image.py: sign the payload`), flash usage is now measured against a proper slot0/slot1 split (`258676 / 499200 B, 51.82%` — roughly half of the 1MB flash per slot, the other half being the second slot for swap-based updates plus MCUboot itself), and a `dfu_application.zip` update package was generated automatically — the direct analog of stravaV10's own `nrfutil`-produced DFU zip.

**Validated on real hardware**: flashed the full image set (`merged.hex` = MCUboot + signed app) via the existing J-Link path. Console shows MCUboot booting first (`*** Booting MCUboot v2.3.0-dev... ***`), correctly reading both slots' state, and handing off (`I: Jumping to the first image slot`) — then the *entire* application from every prior phase runs correctly afterward: sensors, storage, display, GPS UART, ANT+, BLE, the Phase 8 scheduling demos, and USB CDC-ACM (which this run additionally shows genuine host-driven enumeration traffic for — `Configuration enabled`, `CDC ACM line coding` — since the Phase 9 USB cable was still connected).

**Not attempted, and why**: actually performing a DFU update (uploading a new signed image over a running transport and watching MCUboot swap to it) needs an MCUmgr SMP server compiled into the app plus a client (the `mcumgr`/`nrfutil` host tooling) driving it over BLE, USB, or UART — a real additional feature, not just a config flag, and a reasonable next step rather than something to rush into the same session as getting the bootloader itself working.

**RTT tooling on this machine turned out to be unreliable, and needed real debugging, not just "add more buffer"**: Segger's own CLI tools (`JLinkExe`, `JLinkRTTLogger`) segfaulted intermittently on this machine (this installed build is oddly dated "compiled Sep 2 2026" — plausibly a nightly/beta build) — confirmed via `nm` that JLinkExe's own crash was unrelated to the target (repeated `JLinkExe` connect/register-dump scripts against the board consistently showed a live, non-faulted CPU: `CFSR`/`HFSR` both `0`, `CycleCnt` advancing between runs). Switched to `pyocd rtt` (an independent, Python-based implementation) instead — which needed a real TTY (`script -qec "pyocd rtt ..." /dev/null` to fake one; it throws `Inappropriate ioctl for device` otherwise, an environment issue, not a device one) but then reliably found and read the RTT channel via `_SEGGER_RTT`'s linked address (`nm zephyr.elf`, `0x20000410` in this build) once the default in-buffer search alone didn't turn it up.

**Getting a genuinely complete capture took three real fixes, not one**, found by reading the actual captured output at each step rather than assuming a bigger number would fix it:
1. **`CONFIG_SEGGER_RTT_BUFFER_SIZE_UP` 1024 → 2048** — the default up-buffer was too small for the burst of demo output (qspi/display/gps/ant/ble init all firing within milliseconds of boot) to fit before a slow host-side reader could drain it; recovered most, but not all, of the previously garbled/missing output.
2. **`CONFIG_SEGGER_RTT_MODE_BLOCK_IF_FIFO_FULL=y`** (user's fix, replacing the default `NO_BLOCK_SKIP` on buffer 0, shared by `printk`/`RTT_CONSOLE` and the `LOG_BACKEND_RTT` backend) — skip mode was silently dropping output once the enlarged buffer still filled faster than the reader drained it, which is what the log's own `--- 1 messages dropped ---` line was reporting. Blocking trades that for the firmware pausing on RTT writes with no reader attached — correct for a bring-up/debug build, not something to ship in a production image.
3. **Realized nRF52840 SRAM — including the `_SEGGER_RTT` control block and its queued-but-undrained content — survives a `west flash`/SWD soft reset**, and `SEGGER_RTT_Init()` deliberately preserves an already-initialized control block rather than resetting it (so a live debugger session isn't disrupted by the target resetting). Combined with blocking mode, this meant every capture after the first replayed whatever backlog had accumulated *before* the reader attached (real observed case: 3+ minutes of queued ANT+ reconnect-cycle messages) ahead of the actual fresh boot output. Fixed by explicitly zeroing the `SEGGER RTT` magic bytes at the control block's address via a `JLinkExe` script (`halt` / `w4 <addr> 0` ×3 / `r` / `g`) immediately before attaching the reader, forcing `SEGGER_RTT_Init()` to treat it as uninitialized and reset cleanly — and running the clear-and-capture as one uninterrupted shell sequence, since any gap between them let a new backlog start accumulating again under blocking mode.

**Found and fixed — the board has a self-power-latch that this port wasn't holding, causing it to power itself off mid-session.** The user identified the mechanism: the board's regulator stays on only while its STC3100 fuel-gauge chip's IO0 pin is actively driven, a fact stravaV10's own code confirms — `source/sensors/STC3100.cpp`'s `reset()`/`init()` sequence (`REG_CONTROL = STC_RESET`, then `REG_MODE = MODE_RUN`) leaves IO0 actively driven (holding the latch); `shutdown()` (`REG_MODE = 0`, then `REG_CONTROL = STC_IO_OD`) deliberately releases it to open-drain to let the board power itself off, and `power_scheduler.cpp`'s real idle-timeout path calls exactly that `stc.shutdown()`. Since no Zephyr driver for the STC3100 exists yet (Phase 3 gap) and nothing in this port had ever talked to it, the chip sat in its power-on-reset default — which doesn't hold the latch — and the board lost power on its own partway through a test session (`VTref` read `0.000V` on the J-Link probe, confirmed as a real power loss, not a debug-tooling fault, by also checking `nrfutil device list` no longer showing the board's own USB enumeration).

Fixed with a minimal, targeted addition in `main.c` (`stc3100_power_latch_hold()`, called as the very first line of `main()` — every millisecond before it runs is a millisecond the board risked losing power): two raw `i2c_write()` calls replicating only stravaV10's own `init()` register writes (`STC3100_REG_CONTROL = 0x02`, then `STC3100_REG_MODE = 0x10`) against the existing sensor I2C bus (`arduino_i2c`) at address `0x70` — not a real STC3100 driver, just enough to hold power. Harmless on the DK: the same bus `i2c_demo()` already scans there, just cleanly NACKed since nothing is at that address.

**Validated on real hardware**: confirmed the write actually reaches the chip (the log line `stc3100: power latch held (CONTROL reset, MODE run)` appears on every boot), then confirmed power genuinely holds — `VTref` stayed at a stable ~3.35V a full 200+ seconds after boot, well past the point where the board previously lost power without this fix, with the rest of the boot sequence (sensors, storage, display, ANT+, BLE, USB, task/power/poll demos) all still completing normally afterward.

**Update — QSPI NOR flash memory-mapped (XIP) mode added and validated with a 256KB round trip.** Zephyr's `nrf_qspi_nor.c` driver only models the chip as a `flash_read()`/`flash_write()` device by default; the nRF52840's QSPI peripheral can additionally map the external chip's contents straight onto the CPU's memory bus for reads (Nordic's `NRF_MEMORY_EXTFLASH_BASE`, `0x12000000` — not discoverable from devicetree, since no DT node models this window, so it's hardcoded in `main.c`'s `qspi_xip_demo()` with a comment citing its source), toggled at runtime via the driver's own `nrf_qspi_nor_xip_enable(dev, true/false)` (found via Zephyr's own `tests/boards/nrf/xip` ztest, the only in-tree usage example — that test itself only targets nRF5340, but the underlying driver code path is shared and unconditional for nRF52840 too, just without the separate `XIPEN` register bit newer chips have).

`qspi_xip_demo()` (called from `storage_demo()` right after the existing `qspi_flash_demo()`) is a genuinely larger test than anything else in this port's storage validation so far: erases and writes 256KB (64x the size of the pre-existing 16-byte pattern test, spanning 64 4KB sectors) with a per-byte multiplicative-hash pattern (deliberately not a repeating/incrementing pattern, so a stuck bit or a misaddressed region anywhere in the span shows up as a mismatch instead of hiding behind a repeated value), verifies it once via the normal `flash_read()` API as a baseline, then enables XIP and re-verifies the identical 256KB by dereferencing it directly as memory at `0x12000000` — the actual point of the test, proving the memory-mapped window reflects the real chip contents, not just that the normal API still works.

**First design used USB CDC-ACM for the command channel (matching Phase 9's existing console), but real-hardware testing surfaced a genuine, non-firmware root cause**: every host-side write to `/dev/ttyACM0` stalled for a consistent ~35 seconds, regardless of payload size (confirmed with single-byte writes) — traced to the host machine's **ModemManager** service, not this port's code. `udevadm info -n /dev/ttyACM0` showed `ID_MM_CANDIDATE=1`: ModemManager treats any generic CDC-ACM interface (this board's VID:PID `2fe3:0002` included) as a modem-probe candidate, opening the port and sending AT-command probes on its own — matching the repeated spurious `CDC-ACM DTR: 1/0/1` transitions already visible in earlier RTT captures, and plausibly also corrupting/eating command bytes gps_sim_demo's tiny line parser was supposed to see cleanly. Permanent fix (a udev rule ignoring just this VID:PID, `ENV{ID_MM_DEVICE_IGNORE}="1"`) is recorded in the repo-root `todo.md`, not yet applied.

**Switched the command channel to the RTT down channel instead** (`src/gps_sim_demo.c`'s `cmd_poll_work_handler` now calls `SEGGER_RTT_Read(0, ...)` directly rather than `uart_poll_in()` on the CDC-ACM device) — channel 0's down side ("Terminal", paired with the up side this port's console/log backends already write to) is untouched by any other code in this port (`rtt_console.c`/`log_backend_rtt.c` only ever write the up side), and this project's own tooling (`pyocd`) already speaks RTT for every capture, so this sidesteps the ModemManager issue entirely rather than working around it. Sending a command from the host no longer goes through a shell redirect into `/dev/ttyACM0`; instead it uses pyocd's `RTTControlBlock`/`RTTUpChannel`/`RTTDownChannel` classes directly from a small script (drives the exact same underlying mechanism `pyocd rtt` uses, minus that command's interactive-keyboard loop, which needs a real TTY and was the reason earlier captures in this project used a `script -qec ... /dev/null` fake-TTY wrapper).

**Validated on real hardware**: flashed, sent `"SIM START"` over the RTT down channel, and captured the up channel — `Locator::getPosition()` correctly returned `eLocationSourceGPS` (`Locator update source: 3`) with a continuous stream of `locator: GPS fix lat=... lon=... alt=...speed=...course=...` lines tracking real injected coordinates (progressing eastward, speed in the high-20s/low-30s km/h, course ~90-99°) matching the known route's character (avg ~29.7km/h, real road-cycling data) — all while every other Phase 2-11 subsystem (ANT+, BLE, USB enumeration, task/power/poll demos, display) kept running correctly alongside it, same as every other concurrency check in this port.

### Maps feasibility study (research only, no code)

`docs/maps_feasibility.md` — whether/how to add on-device map rendering. Bottom line: feasible as a genuinely new subsystem (this codebase has no map-rendering code — `komoot_nav.c` is just phone-driven turn icons over BLE, already out of scope, and `Zoom.cpp` is dead scaffolding never wired to any screen). Recommended architecture: vector street rendering from a custom compact binary format (not raster tiles, not a general format like Mapbox Vector Tiles — both wrong for a 256KB-RAM/1bpp-display MCU), converted offline from OSM data via `osmium`, stored on the SD card (the only store with realistic capacity — QSPI NOR's 16MB is too small for a real riding area). Grounded in real precedent, not just theory: independent hobbyist projects (`bike-computer-32` on ESP32-C3, a genuinely comparable RAM tier) already do exactly this with a custom format, not an existing library. First identified risk: SD card FAT filesystem was unproven (only raw sectors tested) — see below, now resolved.

**Update — SD card FAT filesystem mount validated on real hardware, resolving the maps study's first open risk.** Added `sd_fat_demo()` to `stravaV11_fw/src/main.c`, called right after `disk_raw_ioctl_demo("SD")` in `storage_demo()`: mounts `CONFIG_FAT_FILESYSTEM_ELM` at `/SD:` (new `prj.conf` config: `CONFIG_FILE_SYSTEM=y`, `CONFIG_FAT_FILESYSTEM_ELM=y`), does the same unmount/remount cycle Zephyr's own `samples/subsys/fs/fs_sample` does immediately after a successful mount (before any file I/O), then a real file create/write/close/reopen/read/verify round trip, then lists the root directory. `CONFIG_FS_FATFS_MOUNT_MKFS` (Kconfig default `y`) means a card with no valid FAT boot sector gets auto-formatted on mount rather than just failing — expected and desired here, since `disk_raw_ioctl_demo()`'s own raw-sector-0 test (which runs first) overwrites the boot sector with non-FAT pattern data on every single boot.

**One real bug found and fixed while validating, not a mount/mkfs problem at all**: the first attempt used the filename `stravav11_test.txt` and got `fs_open() -> -2` (`-ENOENT`) on every attempt, even though `fs_mount()`, the remount, and `fs_opendir("/SD:")` all succeeded (root listed as empty, correctly, for a freshly-mkfs'd volume). Traced through `zephyr/subsys/fs/fat_fs.c`: `translate_error()` maps `FR_INVALID_NAME` to `-ENOENT`, and that name (11 characters before the extension) isn't valid 8.3 short-filename format — `CONFIG_FS_FATFS_LFN` (long filename support) isn't enabled. Fixed by using an 8.3-compatible name (`STRAVA11.TXT`) rather than enabling LFN, since nothing about this validation actually needed long filenames.
