# Port history

Full phase-by-phase narrative for the stravaV10 → nRF Connect SDK/Zephyr port: what was tried, what broke, root causes, and how each thing was validated. This is the detailed log that used to live inline in `CLAUDE.md`; it was moved here 2026-09-11 to keep `CLAUDE.md` itself down to current-state guidance. `CLAUDE.md` has a condensed current-status summary with pointers into the matching section below — read this file when you need the "why" behind a decision, a bug's root cause, or exact validation evidence, not just the current state.

## Phase 1 status: business-logic port (done, validated on both native_sim and the DK)

`stravaV11_app/lib/` holds copies (not symlinks — `stravaV10` stays untouched as the reference) of the hardware-agnostic tier identified in the architecture survey: `source/routes/*`, `source/model/{PowerZone,RRZone,SufferScore,UserSettings}`, `source/display/{SegmentManager,Zoom}`, `libraries/{kalman,VParser,komoot,filters,utils}`, plus the small SDK16 wrapper headers (`segger_wrapper.h`, `math_wrapper.h`, `assert_wrapper.h`, `task_manager_wrapper.h`) — these are kept building under `-DTDD`, reusing stravaV10's existing host-build abstraction (they already compile to hardware-free stubs that way) rather than writing new Zephyr-native shims prematurely; that substitution is follow-up work for when the driver phases land. `src/main.cpp` is a smoke test (not a ztest suite yet) exercising each ported piece; output is bit-identical between native_sim and the flashed DK.

Three things worth knowing if you touch this again:
- **`libraries/filters/order1_filter.c` was swapped for `TDD/order1_filter_tdd.c`.** The former is the real ARM CMSIS-DSP implementation (references a `.instance` struct member that only exists in the non-`TDD` branch of `order1_filter.h`) — stravaV10's own CMakeLists.txt already substitutes the TDD variant for host builds; we do the same.
- **`Point::objectCount` / `Point2D::objectCount2D`** (static members declared in `Points.h`) are defined in stravaV10's `Model.cpp`, not `Points.cpp` — an artifact of Model.cpp being the catch-all file, not a bug. Since Model.cpp isn't ported, these two one-line definitions live in `src/globals.cpp` instead, along with the `UserSettings u_settings` global instance that `PowerZone::addPowerData()` reads FTP from.
- **Adapters for the two real hardware calls this tier still makes**, in `stravaV11_app/adapters/`: `notifications_segNotify()` (drives the WS2812 status LED from `SegmentManager`) no-ops; `fram_read_block()`/`fram_write_block()` (from `UserSettings::sync()`/`writeConfig()`) return `false`, so settings never persist and always fall back to `resetConfig()`'s in-memory defaults. Both get replaced for real once the LED and FRAM driver phases happen. `ant_device_manager.h` here is also a placeholder — just the four default ANT device-number constants `UserSettings::resetConfig()` needs, not the real header (which pulls in the full ANT stack via `ant.h`).

Not part of this slice, and why: `Model.cpp` (the hardware/connectivity orchestrator), `Boucle*.cpp` (ride-mode controllers — `Boucle.cpp` itself pulls in the task manager, global `vue`/`stc` objects, and `g_structs`-based error state; `BoucleFEC.cpp` pulls in ANT+ FE-C and BLE), `Attitude.cpp`/`Locator.cpp` (need the FXOS sensor driver and TinyGPS++ integration respectively — Locator was ported later, see Phase 6/11), `UserSettings`'s FRAM persistence, and all connectivity (`ble_services`, `ant_profiles`) — these need actual driver/connectivity phases first, per the phased plan.

## Phase 2 status: DK driver bring-up (done)

`stravaV11_fw/` is a second, separate application (not merged into `stravaV11_app`) for hardware bring-up on the nRF52840-DK: GPIO/LED/button and the LS027 display. It's kept separate because it depends on DK-specific devicetree (an `&arduino_spi` node, a `zephyr,display` chosen node) that doesn't exist on `native_sim` — mixing it into the native_sim-validated logic app would break that app's portability. The two apps get merged once both are mature.

Key finding: **Zephyr already has an upstream driver for this exact display.** `zephyr/drivers/display/ls0xx.c` (devicetree compatible `sharp,ls0xx`) explicitly lists `LS027B7DH01A` as supported hardware, and its binding's `serial-vcom-inversion` property matches stravaV10's own `drivers/lcd/ls027.c` approach (VCOM toggled in-band over SPI, no EXTCOMIN pin) — so no custom driver was needed, just a devicetree overlay (`stravaV11_fw/boards/nrf52840dk_nrf52840.overlay`) wiring a `sharp,ls0xx` child node (400x240, `serial-vcom-inversion`) onto the DK's Arduino-header SPI bus (`arduino_spi`/spi3). There's also a matching Zephyr shield (`boards/shields/ls0xx_generic`) but it defaults to a different variant (128x128, hardware EXTCOMIN) — not a match for our wiring, hence the hand-written overlay instead of `-DSHIELD=`.

**Validated on real hardware** (bare DK, nothing external attached): GPIO (on-board LED/button), UART (the console itself proves this), I2C (full address scan, 112 clean NACKs, 0 ACKs, bus never hangs), SPI + display (`spi_is_ready_dt()` passes, `display_write()` returns 0 for a full-frame test pattern).

**Not validated on the DK, and couldn't be until physically wired up:** real SPI framing correctness on actual glass, or the final custom-PCB pin mapping (the overlay's pins are arbitrary DK Arduino-header pins). Resolved later on the real custom PCB (Phase 11).

## Phase 3 status: sensors (bme280/fxos8700/FRAM done via upstream drivers; ms5637/VEML6075 need custom drivers, low priority; STC3100 got a real custom driver in a later update)

Added to `stravaV11_fw`'s overlay/prj.conf/main.c, same bare-DK caveat as the display (nothing physically attached, so these validate clean init/error paths, not real readings):

- **`bme280`** (0x76) — Zephyr's upstream `bosch,bme280` driver, direct reuse. This is stravaV10's *active* barometer (`BARO_TYPE bme280` in `source/parameters.h`); `ms5637.c` in stravaV10 is an alternate-BOM option for different hardware revisions and shares the same 0x76 address (the two are never populated on the same board).
- **`fxos8700`** (0x1e) — Zephyr's upstream `nxp,fxos8700` driver, direct reuse.
- **FRAM → `fujitsu,mb85rcxx`** (0x50, `address-width = 8`, `size = 2048`) — reused, not custom-built. Traced stravaV10's `source/sensors/fram.c` addressing scheme (`twi_address |= (block_addr & 0x700) >> 8`) against the Zephyr driver's `mb85rcxx_translate_address()` (`cfg->i2c.addr + (offset >> cfg->addr_width)`) and confirmed they're the same scheme — not a guess.

**Still need real custom Zephyr drivers** (genuine remaining work, low priority):
- **`ms5637`** — Zephyr's `drivers/sensor/meas/ms5607` (a sibling chip) is **not** a safe alias: the second-order low-temperature compensation term differs from stravaV10's own `ms5637_compute_t_p()` (`sens2 = 29 * tx / (1<<4)` vs the ms5607 driver's `SENSi = 2 * temp_sq`) — aliasing would build/run fine but silently mis-read below 20°C. `ms5637` isn't even the active barometer choice, so low priority.
- **`VEML6075`** (UV sensor) — no upstream analog; Zephyr's `veml7700`/`veml6031`/`veml6046` are different parts. **Correction found later (Phase 11 real-PCB testing): this sensor does not appear to be actually populated on the real board** (see `project_hardware_and_status_corrections` memory) — CLAUDE.md's earlier "genuinely part of the active hardware" claim was wrong; treat as unconfirmed/likely-not-present rather than a real gap.

**`STC3100`** (fuel gauge/coulomb counter, 0x70) — no upstream analog initially. A real custom driver (`stravaV11_fw/lib/stc3100.{h,c}` + `src/stc3100_demo.{h,c}`) was added 2026-09-07, porting stravaV10's `computeVoltage()`/`computeCharge()`/`computeCurrent()`/`computeTemp()`/`computeCounter()`/`percentageBatt()` math against a 1Hz `k_work_delayable` I2C poll. Wired onto the LIVE DATA screen (`BATT %d%%`) and a `cmd_console.c` `"BATT"` introspection command. **Validated on the real custom PCB**: physically plausible, stable readings across repeated queries (`voltage=4104 mV current=0 uA charge=67 uAh percent=92%`, etc.), consistent with a near-full Li-ion cell, running concurrently with the full stack with zero faults. Not ported: `getAverageCurrent()`/`resetCharge()` (no caller yet) and the soft-reset-after-5s-uptime behavior (no UI lifecycle to key off yet).

A separate, boot-critical use of this same chip (the board's self-power-latch) is covered under Phase 11 below — don't confuse the two: the power-latch write is not this fuel-gauge driver, it's a minimal two-register write done first-thing in `main()`.

## Phase 4 status: storage (done — real hardware validated for flash, SD stays a clean-failure placeholder until Phase 11's real board)

- **QSPI NOR flash — fully validated on real hardware, not just a clean-init check.** The nRF52840-DK has a genuinely populated on-board QSPI NOR chip (MX25R6435F, 64Mbit, `&qspi`/`mx25r64`, no overlay needed). `qspi_flash_demo()` does a real `flash_erase()` → `flash_write()` → `flash_read()` round trip and the pattern comes back byte-for-byte correct. stravaV10's own external flash is a different chip (MT25QL128, `libraries/SST/mt25.c`) but the same JEDEC SPI-NOR-over-QSPI family, so this is a legitimate stand-in.
- **Original plan was FAT-over-QSPI-flash** (`zephyr,flash-disk` + `disk_access` + `CONFIG_FAT_FILESYSTEM_ELM`) but hit a real NCS-specific wall: this workspace's Partition Manager is unconditionally active, and `flashdisk.c`'s build only works for partitions PM itself allocated with "disk" affiliation metadata — a hand-written devicetree `fixed-partitions` node isn't visible to PM's scan (`PM_FOREACH_AFFILIATED_TO_disk` expands to nothing). Real fix would be a `pm_static.yml` statically registering the partition — not done; descoped to the direct flash API instead, which still proves the chip works.
- **SD card over SPI** on the DK (placeholder pins, nothing attached) — cleanly reports "no card" rather than hanging. Real SD card round-trips were later validated on the actual custom PCB (Phase 11).

## Phase 5 status: connectivity (ANT+, BLE central, ANT+ profiles) — all done and validated on real hardware

**ANT+ feasibility (research)**: Nordic's sdk-nrf ships zero ANT+ code. ANT+ requires a separate, access-gated add-on: "ANT for nRF Connect SDK" (https://ant-nrfconnect.github.io/, published by ANT Wireless/Garmin), v2.1.1, explicitly supports nRF52840. Its documented compatibility matrix pairs sdk-nrf v3.2.4 with sdk-ant v2.1.0/2.1.1 — this workspace started on v3.3.4 instead (see the real consequence of that gap under Phase 11: a real MPSL crash pairing an actual ANT+ device, eventually fixed by downgrading to v3.2.4). Concurrent ANT+BLE operation ("Multiprotocol: ANT and Bluetooth LE") is a documented, real Nordic use case via MPSL. Access is a free "ANT+ Adopter" account (GitHub-authenticated license agreement), no cost for a hobby project. Requires the 32.768kHz LF crystal, already present on both the DK and the custom PCB.

Ecosystem context: Garmin ended the ANT+ certification/paid-membership program 2025-06-30 (EU Radio Equipment Directive now requires authenticated/encrypted personal-data wireless transmission; ANT+'s optional encryption isn't universally enforced, so Garmin wound the program down rather than break compatibility). Free Adopter tier/docs/SDK remain available; industry commentary describes the ecosystem as declining. User's call: proceed with ANT+ regardless.

**BLE central — Cycling Power Service client**: `ble_cp_c` ported to `stravaV11_fw/lib/bt_cp_client.{h,c}`, modeled on NCS's own `bt_hrs_client` (no ready-made CPS client exists upstream) and `nrf/samples/bluetooth/central_and_peripheral_hrs`. Wire-format parsing (`cp_measurement_parse()`/`cp_vector_parse()`) is a direct port of stravaV10's `power_measure_decode()`/`power_vector_decode()`. Hit and fixed one real bug: `bt_scan_filter_add()` failed with `-ENOMEM` until `CONFIG_BT_SCAN_UUID_CNT=1` was set (Kconfig default is 0 filter slots). Fully validated later with a real Favero Assioma PRO power meter: connected in ~13s, streamed genuinely live varying wattage including a real `0 W -> 3 W -> 0 W` transition matching light pedal force, confirming `cp_measurement_parse()` decodes real notification payloads correctly. `cp_vector_parse()` remains unverified (this pedal doesn't expose the optional Vector characteristic). An earlier attempt against a real Tacx Neo 2T trainer never connected across ~10 minutes of testing — inconclusive, most likely explained by the trainer's weak/marginal RSSI (-83dBm) or it sitting idle/unpedaled, not a `bt_cp_client` defect (the mechanism was later proven to work against both the Assioma pedals and, separately, this same strap's own BLE/HRS side).

`ble_lns_c` (Location and Navigation Service) and `ble_komoot_c` (custom Komoot navigation service) are **out of scope by user decision (2026-09-06) — not being ported.** `bt_cp_client` is the only BLE central profile from stravaV10 that's part of this port.

**ANT+ stack integration**: user obtained ANT+ Adopter access, downloaded `sdk-ant-2.1.1`, copied into this workspace at `ncs/ant/` (**gitignored, never commit — proprietary, license-gated vendor source**). Consumed via `ZEPHYR_EXTRA_MODULES` (has its own `zephyr/module.yml`) rather than a west manifest import, avoiding a workspace-topology conflict (sdk-ant's own `west.yml`, used only as manifest root, pins v3.2.4). Hit and fixed a real, narrow version-gap bug: `ant/Kconfig`'s `ANT_LIB_DIR` computed empty because it checked the since-deprecated `SOC_SERIES_NRF52X` instead of the renamed `SOC_SERIES_NRF52` — fixed with a one-line local patch (`default "nrf52" if SOC_SERIES_NRF52X || SOC_SERIES_NRF52`); not upstreamed since `ant/` isn't tracked here. A minimal wildcard-RX test (`stravaV11_ant/`) and later the combined `stravaV11_fw` build both validated ANT+ init and channel-open on real hardware, and ANT+ + BLE running concurrently for 15+ seconds with no conflict (call order: `ant_demo_start()` before `ble_demo_start()`, matching sdk-ant's own `ble_ant_app_hrm` reference sample).

**ANT+ device profiles (HRM/BSC/FEC)**: sdk-ant ships ready-made `ant_hrm`/`ant_bsc` profile libraries (reused directly, same field/macro names as stravaV10's `rf/hrm.c`/`rf/bsc.c`, since both descend from the same historical Nordic codebase) but no FE-C library at all, so FE-C (`stravaV11_fw/lib/ant_fec.{h,c}` + `src/fec_demo.{h,c}`) carries stravaV10's own `ant_fec_page_16/25/49/51.c` wire-format logic over directly, same "keep the wire format, rebuild the plumbing" approach `bt_cp_client.c` used. Channel numbering: wildcard=0, BSC=1, HRM=2, FEC=3 (matching stravaV10's own `rf/ant_device_manager.h`). Device numbers kept from stravaV10 initially (`HRM_DEVICE_NUMBER=17334`, `BSC_DEVICE_NUMBER=15568`/type `0x79`, FEC `TACX_DEVICE_NUMBER=15568`); HRM was later switched to the real strap's actual discovered ID `47359` (see Phase 11). `glasses.c` (custom display-glasses ANT+ protocol) remains the one unported ANT+ profile — needs a "do we still want this" check before porting.

Real bug found and fixed while porting BSC: stravaV10's own `SPEED_COEFFICIENT` doesn't divide by `BSC_MM_TO_M_FACTOR` (1000) — a genuine pre-existing dimensional bug making stravaV10's own speed 1000x too large. Verified by unit derivation and cross-checked against sdk-ant's own `bsc_rx` sample (which does include the `/1000` term); this port uses the corrected coefficient.

All three profiles validated on real hardware for clean init/open (no live sensor was broadcasting for HRM/BSC/FEC's very first hardware tests); HRM was later fully validated end-to-end with a real strap once the Phase 11 MPSL/ANT+ version-gap crash was fixed (see Phase 11).

**ANT+ device manager (pairing/search)**: `rf/ant_device_manager.cpp` ported as `stravaV11_fw/lib/ant_device_manager.{h,c}` (portable candidate-list bookkeeping) + `src/ant_dm_demo.{h,c}` (Zephyr channel orchestration). Uses a dedicated background-scan (BS) channel 4 (channel 0 is already held by the permanent wildcard RX demo) with sdk-ant's extended-message feature (`ant_lib_config_set(...INC_RSSI|INC_DEVICE_ID)`) for per-device visibility on a wildcard-listening channel — found via sdk-ant's own `ant_bgnd_scan` sample; this port's version is stricter than stravaV10's own unconditional `ant_evt_bs()` (adds a bitfield check). Console commands: `"DM SEARCH HRM/BSC/FEC"`, `"DM LIST"`, `"DM PICK <n>"`, `"DM CANCEL"`. Real bug found and fixed on hardware: the first version didn't close the BS channel before reprogramming it for a new search, failing `ant_channel_open()` with `16405` (already open) on a second search without an intervening cancel/pick — fixed by adding an unconditional `ant_channel_close()` at the top of `search_start()`, matching stravaV10's own behavior. Validated on the real PCB: search-start/list/pick error paths all behave correctly with no candidates present, and the search-transition sequence (BSC→FEC→CANCEL→HRM) works cleanly after the fix. **Not ported**: UserSettings/FRAM persistence of the chosen device number (UserSettings isn't wired into `stravaV11_fw`), so a validated pairing only lasts until reset. **Not yet validated**: the actual "candidate found → PICK → profile channel reprogrammed → re-pairs" end-to-end path (no sensor was broadcasting during that specific test).

**Real ANT+ license key**: `stravaV10`'s hardcoded `CONFIG_ANT_EVALUATION_KEY=y` was silently in effect for every hardware run up to a point, since sdk-ant reads `CONFIG_ANT_LICENSE_KEY` directly (a header define has no effect). Fixed in `stravaV11_fw/CMakeLists.txt`: reads the user's gitignored `ANT_license.h` before `find_package(Zephyr)`, regex-extracts the key, writes a generated Kconfig fragment, sets it as `EXTRA_CONF_FILE` (overriding `prj.conf`'s default). Falls back to the public evaluation key with a `message(WARNING ...)` if the header is missing, so the build never hard-fails. Validated: the compiled `CONFIG_ANT_LICENSE_KEY` no longer matches the known public evaluation key string.

## Phase 6 status: GPS (logic tier done and verified correct on native_sim; hardware UART tier clean-only until Phase 11's real GPS module)

Ported `libraries/TinyGPSPlus/TinyGPS++.{h,cpp}` unmodified, plus a trimmed `source/model/Locator.{h,cpp}` (dropped `locator_dispatch_lns_update()` — dead code since `ble_lns_c` is out of scope; dropped `displayGPS2()` — that's `vue`/LS027 UI, belongs to Phase 7; dropped two `w_task_events_set()` calls — no Boucle consumer exists yet). `source/model/Sensor.h` (the freshness-tracking wrapper) ported unmodified. `GPS_MGMT` stubbed in `adapters/gps_mgmt_stub.cpp` (only the three methods Locator calls). New `adapters/millis_zephyr.c` (`k_uptime_get()`/`k_msleep()`/`k_busy_wait()`) — deliberately not bridged via either of stravaV10's own `millis.c` (app_timer-coupled) or the TDD scheduler (would reintroduce the task-manager category Zephyr replaces).

**Verified correct, not just "builds"**: `stravaV11_app`'s smoke test feeds two real NMEA sentences (TinyGPSPlus's own `FullExample` fix, 30.14°N 97.49°W) character-by-character through `locator_encode_char()`, and `Locator::getPosition()` returns the correctly decoded lat/lon/speed matching hand-computed values (checksums were computed fresh via a one-line Python XOR — the first attempt had a wrong checksum and was correctly rejected, itself confirming checksum validation works).

Hardware tier (`stravaV11_fw`): `arduino_serial` (uart1) enabled at 9600 baud via overlay; `uart_demo()` sends stravaV10's real `$PMTK220,200*2C\r\n` fix-interval command and polls RX — validated clean TX/RX with nothing attached on the DK. GPS_R/GPS_S/FIX_PIN weren't wired up yet at this point (done in Phase 11).

## Phase 7 status: UI graphics (AdafruitGFX ported unmodified; new ZephyrGFX bridge class; actual screens deferred)

stravaV10's `source/vue/*` (~4500 lines) is a tightly coupled "god class" (`Vue` multiply/virtually inherits `VueCRS`/`VueFEC`/`VuePRC`/`VueDebug`/`NotifiableDevice`/`Menuable`, all sharing one `Adafruit_GFX` base with pure-virtual cross-dependencies) — porting it whole would mean pulling in `Model`/`Boucle*`/buttons/notifications at once. So this phase ported only the genuinely independent piece:

- **`libraries/AdafruitGFX`** ported unmodified (one generic portability fix: `pgmspace.h`'s bare `typeof` → `__typeof__`, unrelated to any SDK version gap).
- **New `ZephyrGFX` (`source/vue/ZephyrGFX.{h,cpp}`)**: a from-scratch `Adafruit_GFX` subclass implementing `drawPixel()` against an in-memory 400x240 1bpp buffer matching `ls0xx.c`'s expectations (`PIXEL_FORMAT_MONO01`, LSB-first per byte — deliberately different bit order from stravaV10's own MSB-first `ls027.c`). Hardware-free, builds on `native_sim`. Rotation transform was added later (Phase 11) once real glass was available to check against.
- Verified with a real before/after pixel-count check (0 → 1675 after drawing text/shapes) — the first version of this test filled white-on-white and would have "passed" even with a no-op `drawPixel()`, a pattern worth remembering for future pixel/graphics smoke tests.
- Hardware tier (`stravaV11_fw`'s `src/gfx_demo.cpp`): the same scene pushed via `display_write()` to the real `sharp,ls0xx` device — pipeline runs cleanly on real hardware (no physical LS027 attached to the DK at this point, so pixel-level correctness on glass was unverified until Phase 11).

**Not ported, and why**: `Vue`/`VueCRS`/`VueFEC`/`VuePRC`/`VueDebug`/`VueGPS` (the actual screens — ported much later, see the "Phase D" entry under Phase 11), `MenuObjects`/`Menuable`, `Screenutils`, `button.h`/`Notif.h` — all orchestration tightly coupled to `Model`/`Boucle*`/buttons/notifications.

**LS027simulator.jar dev-tool bridge**: `stravaV10`'s own visual dev tool (a Java/Swing app, TCP client at `127.0.0.1:8080` speaking `sGUIComm` frames) was connected to `stravaV11_app`'s native_sim build via a new `adapters/gui_connector.{h,c}` (a matching TCP *server*, POSIX-arch-only, toggled via an `LS027_GUI` env var, not a Kconfig). Two real format differences were reconciled: bit *polarity* (inverted — ZephyrGFX's `1=white` vs. the Java client's `1=black`), and everything else (bit order, dimensions, no buffer-level rotation) already matched. **Validated end-to-end with the real, unmodified jar**: a real screen capture (worked around a Wayland screenshot-portal block via `xwd`) showed the correct rendered scene in the correct rotated portrait orientation — the first visual confirmation of `ZephyrGFX` output, on native_sim.

**Later replaced by a modern Python + Pygame viewer** (`stravaV11_app/tools/ls027_viewer.py`) per user request ("something more modern") — the wire protocol was kept identical, so `gui_connector.c` needed zero changes; only the client changed. Validated pixel-identical to the jar's own earlier screenshot. One bug fixed along the way: Python fully block-buffers stdout when not a TTY, hiding status messages until exit — fixed with `sys.stdout.reconfigure(line_buffering=True)`.

## Phase 8 status: scheduling/power (done — Zephyr threads/k_event/k_work_delayable replacing stravaV10's task_manager/power_scheduler/i2c_scheduler)

- `task_manager` (hand-rolled cooperative scheduler) → Zephyr threads + `k_event` (`task_demo.c`). Not a 1:1 API clone — each logical task gets its own `k_event` object rather than one shared flags-word-per-task-ID indirection. `task_delay()`/`task_tick_manage()` → every Zephyr thread's built-in `k_sleep()`.
- `power_scheduler.cpp` → a Zephyr thread doing the same idle-check logic (`power_demo.c`), 4s demo timeout instead of the real 15-minute constant (belongs at the future Boucle call site). `sys_poweroff()` is available but deliberately not called in the demo (would kill the DK mid-debug with no wake source wired).
- `i2c_scheduler.cpp` (really a periodic-sensor-poll orchestrator, not a generic I2C queue — Zephyr's I2C driver already handles transaction queuing) → a self-resubmitting `k_work_delayable` against the real `bme280` (`poll_demo.c`), at stravaV10's real 100ms poll period.

**Validated together on real hardware** (concurrency was the interesting claim to prove here, not solo operation): all three ran alongside every prior phase simultaneously — 5 clean 100ms-spaced polls, 5 correct producer/consumer event handoffs, and the idle-timeout thread firing at 4001ms mid-run without disturbing the other threads afterward.

## Phase 9 status: USB CDC-ACM (device controller fully validated on real hardware, including host-side enumeration; MSC is a known, explicit gap — later resolved, see the hardware-status-corrections memory)

Only CDC-ACM was ported initially — MSC needs a `disk_access`-registered block device, which Phase 4 deliberately didn't reach (Partition Manager issue) and no SD card was inserted at the time. (Per `project_hardware_and_status_corrections` memory: USB MSC was later actually completed — this CLAUDE.md section is the original, now-stale account of the gap; check that memory before assuming MSC is still missing.)

`stravaV11_fw/src/usbd_init.{h,c}` adapts Zephyr's own `sample_usbd_init.c` pattern but de-sample-ified (defines its own VID/PID/strings — VID `0x2FE3` is still the Zephyr Project placeholder, fine for this bring-up stage, not for shipping). `usb_demo.c` enables CDC-ACM and logs VBUS/DTR transitions, deliberately not blocking on DTR (would hang the smoke test with no host terminal attached). Two real bugs fixed: a stray `*/` inside an explanatory comment corrupting subsequent syntax, and a link-time symbol collision (`LOG_MODULE_REGISTER(usbd_init,...)` colliding with Zephyr's own internal module of the same name — renamed to `stravav11_usbd_init`).

**Fully confirmed on real hardware including host-side enumeration**: `lsusb` showed `ID 2fe3:0002 NordicSemiconductor stravaV11 GPS computer`, and a working `/dev/ttyACM1` appeared distinct from the J-Link's `/dev/ttyACM0` — the strongest hardware validation of any peripheral in this port at the time.

## Phase 10 status: bootloader/DFU (done — MCUboot boots the app; a real BLE/MCUmgr OTA update cycle validated end-to-end)

One line of sysbuild config (`SB_CONFIG_BOOTLOADER_MCUBOOT=y`) — mainline Zephyr's own sysbuild MCUboot integration (devicetree `fixed-partitions`), not NCS's older Partition Manager-based path, so it didn't reopen Phase 4's PM/flash-disk friction. Signed image, slot0/slot1 split, auto-generated `dfu_application.zip`. Validated on real hardware: MCUboot boots first, hands off correctly, and the entire application (every prior phase) runs correctly afterward.

**Real BLE/MCUmgr SMP DFU**: chose BLE over USB/UART (the one UART is dedicated to GPS; CDC-ACM already owns a different line protocol). **Real bug #1: the signed app image was 891 bytes over MCUboot's true maximum image size.** The default partition layout's symmetric 122/122-sector primary/secondary split leaves zero slack — MCUboot's swap-move algorithm (`app_max_size()` in `swap_move.c`) actually reserves an extra sector on top of the trailer for its own bookkeeping, making the true per-slot budget smaller than the raw partition size (invisible to a flat linker FLASH-region percentage check, which is why the earlier "~7.5KB margin" claim never caught this). MCUboot single-slot mode was seriously tried but reverted: it removes Phase 10's whole BLE/MCUmgr DFU capability (not just auto-revert), and hit a genuine NCS integration gap (`'PM_MCUBOOT_SECONDARY_ID' undeclared`).

**Fixed with a static, asymmetric partition layout** (`stravaV11_fw/pm_static_stravav11_nrf52840.yml`): mcuboot's own partition shrinks from 12 sectors/48KB to 11 sectors/44KB (its real build has only ever used 36-39KB), and the freed sector goes to `mcuboot_primary` (123 sectors vs. secondary's 122 — MCUboot's own preferred +1 ratio). Only `mcuboot` and `mcuboot_secondary` need static entries; `mcuboot_primary` must stay unlisted (Partition Manager needs at least one unfixed gap for its own dynamic sub-placement, or it fails with "Incorrect amount of gaps found"). Verified by hand against `app_max_size()`'s formula before writing: both slots land at 495616B, comfortably above the 492411B image with ~3.2KB margin each.

**Real bug #2, found immediately after the board booted cleanly: the LS027 showed a completely blank screen.** A pixel-count diagnostic in `vue_demo.c` showed the buffer staying at exactly 96000/96000 (the full-screen fill, unchanged) every refresh — nothing was ever drawn, not silently failing to draw. This exact bug class had already been fixed once, but only inside the native_sim test harness, never in `vue_demo.c`'s real production init path. **Fixed with one `vue.setTextColor(0)` call.** **Validated and confirmed by the user on the physical panel** ("Fixed, looks right").

## Segments/live-race feature compile-time option (2026-09-11)

Live-segment racing was already descoped by user decision (2026-09-07) — `SegmentManager`/`segMngr` never gets populated with real data anywhere in this port, so no runtime behavior changed by this option either way. **Real, measured flash impact on `stravaV11_fw`**: 501620B → 495984B linked FLASH usage (signed image 502283B → 496648B), a genuine ~5.6KB reduction — this is what directly resolves the Lezyne feature's flash-budget blocker.

**A real, non-obvious sysbuild gotcha hit while testing this**: passing `-DSTRAVA_SEGMENTS_ENABLED=OFF` after `--` on the *initial* `west build` command does not reach the sysbuild sub-image's own CMake cache (confirmed via the sub-image's `CMakeCache.txt` — it stayed ON regardless) — sysbuild's per-image variable forwarding needs an image-name-prefixed variable that wasn't found by guessing. The reliable workaround: build once normally, then re-run `cmake -DSTRAVA_SEGMENTS_ENABLED=OFF <build-dir>/<app>` directly against the already-configured sub-image directory, then `ninja` there. Worth a proper fix (an `SB_CONFIG_`-style sysbuild Kconfig option) if this flag sees regular use.

## Maps feasibility study

`docs/maps_feasibility.md` covers the full research and design writeup. Bottom line: feasible as a genuinely new subsystem (no existing map-rendering code in stravaV10 — `komoot_nav.c` is phone-driven turn icons, already out of scope; `Zoom.cpp` was dead scaffolding until this study wired it up). Recommended/built architecture: vector street rendering from a custom compact binary format (not raster tiles, not Mapbox Vector Tiles — both wrong for a 256KB-RAM/1bpp-display MCU), converted offline from OSM data, stored on the SD card.

Progress, in order: SD card FAT filesystem mount validated on real hardware (one real bug found — an 8.3-filename-format issue, fixed either way once long-filename support (`CONFIG_FS_FATFS_LFN=y`) was enabled and validated). Offline OSM-to-binary-tile conversion tool (`tools/osm_to_tiles.py`, depends on the `osmium` PyPI package) built and validated against a synthetic test PBF (Douglas-Peucker simplification, tile-boundary splitting, road-class filtering all confirmed correct; one real bug fixed — a way that leaves and re-enters the same tile wasn't originally handled). On-device tile parser (`stravaV11_app/lib/source/maps/map_tile.{h,c}`, a stateful iterator directly over the caller-owned buffer, not a bounded-array-copy decoder) validated on native_sim against a real tool-generated tile fixture, then the SD-card `fs_open()`/`fs_read()` loader validated end-to-end on real hardware. Altitude added to the tile format (v2, magic bump — a real breaking change since nothing had shipped real map data yet): sourced from OSM node `ele` tags where present, sentinel `-32768` where absent; validated on both native_sim and real hardware. Live GPS-fix altitude (a different data source from map-tile altitude) also wired onto the LIVE DATA screen and validated with the GPS simulator.

**Map tile rendering** (`stravaV11_app/lib/source/maps/map_render.{h,cpp}`) projects/draws a parsed tile onto a `ZephyrGFX` canvas, finally exercising `Zoom::computeZoom()` (dead code since Phase 1 until now) — zoom is one constant (`MAP_RENDER_ZOOM_LEVEL`, not runtime/button-driven; no pan/zoom input exists). Validated on native_sim against the real tool-generated fixture (caught a real test-assertion-direction bug in the process: filling with black lines *decreases* pixel count on a white background, the opposite of every other `ZephyrGFX` smoke test in this port). Validated on real hardware showing the map for ~1s before the LIVE DATA screen takes over.

**Real OSM map data rendered and confirmed on the physical panel: "I could recognize streets."** Fetched a real extract (Overpass API, bbox covering the GPS-sim route's actual Rotterdam ride), converted (2889 ways seen, 1265 kept, 2 tiles — confirming the route really does cross a tile boundary as predicted) and embedded via a new kept tool `tools/tile_to_c.py`.

**Root-caused why nothing had rendered before this — a real, general bug, not maps-specific.** `Locator::getPosition()` is single-consumer (it clears the update flag as a side effect); `gps_sim_demo.c`'s own replay handler called it immediately after injecting a fix, essentially always winning the race against any other independent poller, so `gps_demo_get_position()`/`get_altitude()` (which also called `getPosition()`) never once saw a fix despite real fixes flowing continuously. **Fixed by reading `gps_loc.data` directly** (no consuming side effect) with `getAge()` for staleness instead of the latching `isUpdated()` — a real, generally-applicable fix for any future code reading Locator's position from more than one place.

Also found while isolating this: a genuine power-on reset (confirmed via `POWER.RESETREAS==0`, ruling out a software crash) a few minutes into a concurrent SD-card+display+ANT+/BLE run — mitigated (not root-caused) by the STC3100 power-latch periodic refresh mentioned under Phase 11 above.

**Fully validated, isolated methodically per explicit user direction**: a flash-embedded-only version (`real_route_tiles.h`, no SD card at all) ran 5 minutes continuously with zero crashes, 146 successful map renders across both real tiles as the simulated route crossed the tile boundary — cleanly separating "does rendering work" from "does the board lose power," and pointing at SD-card usage (not the render/Zoom/Bresenham path) as the more likely power-loss trigger, though not fully isolated from "everything running concurrently" at that point.

**`main()` fully restored plus a new dedicated heavy SD-card stress test (`sd_stress_demo.{h,c}`) — the power-loss question resolved with high confidence.** A ~400-second continuous run with the full subsystem set plus heavy, sustained SD I/O (32KB write+readback every 500ms) produced 461 stress cycles all `MATCH`, 185 successful map renders, and zero reboots/faults — strong evidence the periodic STC3100 power-latch refresh resolved the power-loss issue.

**`map_screen_demo` wired back to the real SD-card round trip** (its original design intent, not the flash-embedded isolation shortcut), after finding **one more real bug: a filesystem mount conflict.** Both `map_screen_demo.c` and `sd_stress_demo.c` independently held their own *persistent* mount on `"/SD:"` — Zephyr's fs layer allows only one mount per path at a time, so whichever started second (`map_screen_demo`) failed silently (`fs_mount()` returning `-EBUSY`, its one failing `printk()` lost in a congested boot-time logging burst), making it look like the module had simply stopped doing anything. **Fixed by mounting, doing one file operation, and unmounting again every cycle** in both modules, instead of holding a persistent mount — the already-proven-safe transient pattern `sd_fat_demo()` used from the start.

**Fully validated on real hardware, ~300-second run with the full subsystem set plus `sd_stress_demo`'s heavy I/O**: 202 successful real SD-card tile loads correctly split across both real tiles as the route crosses the boundary, 202 matching renders, 276 concurrent stress cycles all `MATCH`, zero faults — the first real end-to-end confirmation of the SD-card-backed map path this feature always needed for real-world coverage beyond flash capacity.

## RISC-V sandbox research spike (native_sim only, not wired into `stravaV11_fw`/real hardware)

Independent research track from the phased port: whether guest/"plugin" code can be sandboxed by interpreting it rather than trusting it (e.g. a future user-scriptable notification or screen), without an MMU. Scoped by the user to stay sim-only for now.

**Built**: `stravaV11_app/lib/source/riscv/rv32_emu.{h,c}` — a from-scratch RV32IM interpreter (base integer + mul/div, no A/F/D/C, no CSRs). Isolation is deliberately crude: every fetch/load/store is bounds-checked against one host-owned flat arena (a guest address is a byte offset into it — no MMU/paging), and `rv32_emu_run()` takes an instruction-count budget so an infinite-looping guest can't hang the caller. The only way out is `ecall`, dispatched to a host-registered callback (`rv32_hostcalls.h`'s `HOSTCALL_EXIT`/`DRAW_PIXEL`/`LED_SET`/`DEBUG_PRINT`). No ELF loader — a hand-written linker script places a fixed flat binary at address 0.

**Validated on native_sim, wired into the existing smoke test** (the hostcall handler calls straight into this port's real `ZephyrGFX`/`notifications.c` code, not stand-ins): a real guest binary (with a real emitted `mul` instruction) drove `ZephyrGFX::drawPixel()` and the LED ramp with exactly matching results, and the two isolation-focused test guests trapped exactly as designed — a wild out-of-bounds pointer hit `RV32_ERR_MEM_FAULT` in 3 steps instead of corrupting host memory, and an infinite loop hit `RV32_ERR_INSN_BUDGET_EXCEEDED` at exactly the configured budget instead of hanging.

**Not done yet**: wiring into `stravaV11_fw` for real hardware (RAM budget unsized against everything else already running there), an ELF loader, any guest-side libc beyond two hand-written functions, and a real plugin syscall surface beyond this spike's three placeholder calls.
